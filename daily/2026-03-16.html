SLOとエラーバジェット運用
  • 定義: SLOはサービス品質の目標値、エラーバジェットは許容できる失敗余地。
  • 重要性: 「速度優先か安定優先か」を感覚ではなく数値で意思決定できる。
  • 使い分け: 新機能期は予算を使って学習、障害増加期はリリース抑制に切り替える。
  • よくある誤解: 100%可用性を目指すほど良いという誤解。
  • 3分要点: まず1指標（例: API成功率99.9%）で月次運用を始める。

参考: Google SRE / SLO Monitoring

質問テンプレ: 「SLOとエラーバジェット運用を、定義→重要性→使い分け→誤解→3分要点の順で、実務例つきで教えてください。」
Outboxパターンで整合性を守る
  • 定義: DB更新とイベント発行を同一トランザクションで記録し、後段で確実送信する手法。
  • 重要性: 「DBは更新されたがイベント未送信」の事故を減らせる。
  • 使い分け: 注文確定や課金確定など、通知欠落が重大な境界で優先採用。
  • よくある誤解: メッセージキューがあるなら不要という誤解。
  • 3分要点: Outboxテーブル + 冪等コンシューマをセットで実装する。

参考: Transactional Outbox / Fowler

質問テンプレ: 「Outboxパターンを、定義→重要性→使い分け→誤解→3分要点の順で、実装ステップ込みで解説してください。」
Feature Flagの寿命管理
  • 定義: 機能切替フラグを導入し、段階リリースと緊急切戻しを可能にする運用。
  • 重要性: デプロイと公開タイミングを分離でき、障害時の被害を小さくできる。
  • 使い分け: 実験用フラグは短命、本番安全装置フラグは長命で運用ポリシーを分ける。
  • よくある誤解: フラグを残すほど柔軟性が高いという誤解。
  • 3分要点: 期限日・オーナー・削除条件を作成時に必須化する。

参考: Feature Toggles / LaunchDarkly Docs

質問テンプレ: 「Feature Flagの寿命管理を、定義→重要性→使い分け→誤解→3分要点の順で解説し、運用ルール案もください。」
バックプレッシャー設計
  • 定義: 処理能力を超えた入力を抑制し、システム全体の飽和を防ぐ制御。
  • 重要性: スパイク時の連鎖タイムアウトを防ぎ、サービス停止を回避できる。
  • 使い分け: キュー長上限、同時実行上限、早期429返却を組み合わせる。
  • よくある誤解: オートスケールがあれば不要という誤解。
  • 3分要点: 入口制御と下流保護を同時に設計する。

参考: Reactive Streams / Kubernetes Resources

質問テンプレ: 「バックプレッシャー設計を、定義→重要性→使い分け→誤解→3分要点の順で、実装案付きで教えてください。」
依存関係アップデート戦略
  • 定義: ライブラリ更新をリスク別に分類し、継続的に小刻みに反映する運用。
  • 重要性: 巨大アップデートの破壊的変更リスクを回避できる。
  • 使い分け: パッチは自動、マイナーは週次、メジャーは検証ブランチで計画対応。
  • よくある誤解: セキュリティ更新だけ追えば十分という誤解。
  • 3分要点: 依存の棚卸しを月1で実施し、放置負債を可視化する。

参考: Dependabot / SemVer

質問テンプレ: 「依存関係アップデート戦略を、定義→重要性→使い分け→誤解→3分要点の順で、チーム運用に落とし込んでください。」
