API設計でのIdempotency Key運用
  • 定義: 同一リクエストを識別するキーを付け、重複送信でも結果を一意に保つ設計。
  • 重要性: 決済や注文APIでの二重実行事故を防ぎ、再試行を安全にできる。
  • 使い分け: 副作用のあるPOSTに必須化し、GET/PUTはHTTP意味論に沿って別管理する。
  • よくある誤解: キーを付ければ競合更新まで自動解決できるという誤解。
  • 3分要点: キー保存期間・レスポンス再利用方針・衝突時の扱いを先に決める。

参考: Stripe Docs / HTTP Semantics

質問テンプレ: 「Idempotency Key運用を、定義→重要性→使い分け→誤解→3分要点の順で、API設計例つきで教えてください。」
契約テスト（Consumer-Driven Contract）
  • 定義: 利用側が期待するAPI契約を明文化し、提供側と自動照合するテスト手法。
  • 重要性: マイクロサービス間の破壊的変更を本番前に検知しやすくなる。
  • 使い分け: 依存サービスが多い箇所で優先導入し、E2Eの代替ではなく補完として使う。
  • よくある誤解: 契約テストだけで統合不具合を完全に防げるという誤解。
  • 3分要点: まず高頻度APIの契約1本から始め、CIで破壊的変更をブロックする。

参考: Pact Docs / Martin Fowler

質問テンプレ: 「契約テストを、定義→重要性→使い分け→誤解→3分要点の順で、導入ステップ付きで解説してください。」
Canary Releaseの判断指標
  • 定義: 一部ユーザーへ段階公開し、メトリクス確認後に全体展開するリリース方式。
  • 重要性: 問題の影響範囲を最小化し、ロールバック判断を迅速化できる。
  • 使い分け: 新アルゴリズムや高リスク変更で利用し、単純文言修正は通常配信で十分。
  • よくある誤解: カナリー比率を上げれば検証が速くて常に得という誤解。
  • 3分要点: エラー率・遅延・ビジネスKPIの3軸に閾値を置いて自動判定する。

参考: Canary Release / Kubernetes Deployments

質問テンプレ: 「Canary Releaseを、定義→重要性→使い分け→誤解→3分要点の順で、判定メトリクス設計込みで説明してください。」
観測可能性の3本柱を実務で揃える
  • 定義: メトリクス・ログ・トレースを組み合わせ、障害原因を辿れる状態を作る考え方。
  • 重要性: 検知だけでなく原因特定までの時間（MTTR）を短縮できる。
  • 使い分け: 監視はメトリクス中心、調査はトレース起点、詳細確認に構造化ログを使う。
  • よくある誤解: ダッシュボード枚数を増やせば観測可能性が上がるという誤解。
  • 3分要点: まず共通Trace IDを全レイヤーで通し、相互参照できる形にする。

参考: OpenTelemetry / SRE Workbook

質問テンプレ: 「観測可能性の3本柱を、定義→重要性→使い分け→誤解→3分要点の順で、現場運用に落とし込んでください。」
データマイグレーションの二段階デプロイ
  • 定義: スキーマ変更を互換性を保つ2段階（先に追加、後で削除）で進める手順。
  • 重要性: ダウンタイムや旧新バージョン混在時の障害リスクを下げられる。
  • 使い分け: カラム削除・型変更のような破壊的変更で必須、非破壊変更は通常手順で対応。
  • よくある誤解: マイグレーションは1回のリリースで完了させるべきという誤解。
  • 3分要点: Expand → Migrate → Contractの順を守り、戻せる状態を維持する。

参考: Parallel Change / Flyway Docs

質問テンプレ: 「二段階デプロイ型のデータマイグレーションを、定義→重要性→使い分け→誤解→3分要点の順で、実施チェックリスト付きで解説してください。」
