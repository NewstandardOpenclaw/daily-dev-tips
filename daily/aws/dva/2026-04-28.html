AWS DVA 対策（インプット特化）

対象日: 2026-04-28 (JST) / 試験: DVA-C02
Topic 1DynamoDB 読み取り整合性 + RCU/WCU

定義: DynamoDB の読み取りは Eventually Consistent Read（デフォルト）と Strongly Consistent Read の2種類。強整合は最新反映を保証、ただし同じ項目サイズでもコスト（RCU消費）が実質2倍になりやすい。

重要性: DVA問題では「直後に読んだら古い値だった」「コストが急増した」の原因切り分けで頻出。整合性モードとRCUの関係を同時に問われる。

使い分け: 在庫引当や重複防止など“今この瞬間の正しさ”が必要なら強整合。ダッシュボード表示や遅延許容の参照なら結果整合でコスト最適化。

誤解: 「強整合にすれば常に正解」ではない。グローバルテーブル跨ぎや設計不備（ホットパーティション）は別問題。整合性は万能薬ではない。

3分要点: 問題文で latest value required / read-after-write を見たら強整合を検討。コスト制約が同時にあるなら“どこだけ強整合にするか”を読む。

参照リンク: DynamoDB Read Consistency

実践課題: 1テーブルで結果整合と強整合の読み取りレイテンシ/RCU差を計測し、ユースケース別に採用基準を1枚にまとめる。

Topic 2SQS Visibility Timeout / DLQ / 再試行設計

定義: Visibility Timeout は「受信済みメッセージを他コンシューマから一時的に見えなくする時間」。処理失敗時は再可視化され再配信。最大受信回数超過でDLQへ退避可能。

重要性: DVAは「重複処理」「無限リトライ」「メッセージ消失誤解」をシナリオで問う。Visibility と DLQ をセットで理解しているかが差になる。

使い分け: 処理時間が長いジョブは Visibility を十分長く、ただし過剰に長いと障害検知が遅れる。失敗解析が必要ならDLQ必須。

誤解: 「SQSはExactly-once」ではない（標準キュー）。重複は起き得る前提でアプリ側冪等性を持たせる。

3分要点: 問題文に processed multiple times / messages not deleted が出たら、DeleteMessage漏れ・Visibility不足・冪等性不足・DLQ未設定を優先確認。

参照リンク: SQS Visibility Timeout

実践課題: 同一メッセージの重複受信を意図的に発生させ、冪等キーで二重書き込みを防ぐミニ実装を作る。

Topic 3Lambda 同時実行数（Reserved/Provisioned）とスロットリング

定義: Lambda にはアカウント同時実行上限があり、関数ごとに Reserved Concurrency で上限/確保を設定可能。Provisioned Concurrency はコールドスタート低減が目的。

重要性: DVAでは「急なトラフィックで遅延」「一部関数が他を食い潰す」問題が頻出。性能対策と保護策の選択を問う。

使い分け: 他ワークロード保護には Reserved。低レイテンシ保証には Provisioned。SQSトリガならバッチサイズ/最大同時実行も合わせて調整。

誤解: 「Provisionedを増やせばスロットリング解消」ではない。アカウント上限やイベントソース側設定がボトルネックのことがある。

3分要点: 問題文のキーワードが throttles / cold starts / protect critical function なら、ReservedとProvisionedを目的別に切り分ける。

参照リンク: Lambda Concurrency

実践課題: API系関数とバッチ系関数を同一アカウントに置き、Reserved設定前後でスロットリング発生率を比較する。
