Topic 1

API Gateway の認可方式（IAM / Cognito User Pools / Lambda Authorizer）

定義

API Gateway はメソッド単位で認可方式を設定可能。IAMはSigV4署名、Cognito User PoolsはJWT検証、Lambda Authorizerはカスタムロジックで許可/拒否を判定する。

重要性

DVAでは「誰が呼ぶAPIか」で認可方式を選ばせる問題が頻出。セキュリティ強度・実装コスト・運用負荷の比較が得点源。

使い分け

  • IAM: AWS内のサービス間/社内ツールからの呼び出し向け（署名前提）。
  • Cognito User Pools: モバイル/SPA のエンドユーザー認証を標準機能で処理したいとき。
  • Lambda Authorizer: 独自トークン形式や外部IDPルールを適用したいとき。

よくある誤解

  • 誤解: Lambda Authorizer が常に最強 → 柔軟だがレイテンシ/運用コスト増。
  • 誤解: Cognito を使えば APIキー不要 → APIキーは認可ではなく利用量管理用途。

3分要点

  1. 呼び出し主体（AWS主体/エンドユーザー/独自要件）で方式を決める。
  2. 標準で足りるなら IAM/Cognito を優先し、Lambda Authorizer は必要時のみ。
  3. APIキーは認証認可の代替ではない。
Topic 2

DynamoDB 条件付き書き込み（ConditionExpression）で整合性を守る

定義

ConditionExpression は PutItem/UpdateItem/DeleteItem 実行時に前提条件を評価し、条件を満たす場合のみ更新を許可する仕組み。失敗時は ConditionalCheckFailedException を返す。

重要性

DVAでは「同時更新衝突」「重複登録防止」「在庫の下限管理」など、アプリ側整合性をNoSQLで守る設計が頻出。

使い分け

  • attribute_not_exists(pk): 初回登録のみ許可（重複作成防止）。
  • version = :v: 楽観ロックで上書き競合を検知。
  • stock >= :n: 在庫や残高の負値化を防ぐ。

よくある誤解

  • 誤解: 失敗したら自動で再試行される → 条件失敗は業務ロジックで扱うべき。
  • 誤解: TransactWriteItems を使えば条件式不要 → トランザクション内でも条件式は有効かつ重要。

3分要点

  1. ConditionExpression は「書く前に守る」ためのガード。
  2. 条件失敗はシステム障害ではなく業務上の競合シグナル。
  3. DVAでは式の意味（exists/version/比較）を読めることが必須。
