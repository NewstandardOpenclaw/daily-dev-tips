Lambda Event Source Mapping の Batch Window
  • これは何か: SQS/Kinesis/DynamoDB Streams から Lambda を起動する際、レコードを一定時間まとめてから実行させる待ち時間設定（MaximumBatchingWindowInSeconds）。
  • なぜ重要か: 1件ずつ実行よりも呼び出し回数を減らせるため、コストとスループットを両立しやすい。試験では「遅延を少し許容して効率化」の選択肢として頻出。
  • 使いどころ/使い分け: 低レイテンシが最優先なら短く、ログ集計やバッチ変換なら長め。SQS は可視性タイムアウト、Kinesis は IteratorAge 監視とセットで調整する。
  • よくある誤解: Batch Window を伸ばせば常に最適化できると思い込むこと。実際は処理遅延・再試行時の影響も増える。
  • 3分要点: 「呼び出し効率」と「許容遅延」のトレードオフ設定。CloudWatch 指標（Duration/IteratorAge/Throttles）で継続調整する。

参考: Lambda event source mapping

DynamoDB 条件付き書き込み (ConditionExpression)
  • これは何か: PutItem/UpdateItem/DeleteItem 実行時に条件式を評価し、条件を満たした場合のみ書き込みを許可する制御。
  • なぜ重要か: 楽観的ロックや重複登録防止をアプリ側トランザクションなしで実現できる。DVAでは競合回避の定番。
  • 使いどころ/使い分け: 初回作成のみ許可（attribute_not_exists）、バージョン一致更新、在庫の負数防止。複数テーブル整合性が必要なら TransactWriteItems へ。
  • よくある誤解: 条件失敗を例外扱いして終わること。実務では再取得→再試行・ユーザー通知などの分岐設計が必須。
  • 3分要点: ConditionExpression は「壊さない更新」の第一手。競合前提でリトライ戦略まで設計する。

参考: Condition expressions

API Gateway ステージ変数とデプロイ分離
  • これは何か: API Gateway のステージごとに値（エンドポイント、Lambda エイリアス名など）を持たせ、同じ API 定義で環境差分を切り替える仕組み。
  • なぜ重要か: dev/stg/prod を単一構成で管理しつつデプロイ事故を減らせる。試験で「最小変更で環境分離」問題に効く。
  • 使いどころ/使い分け: Lambda エイリアス切替、バックエンド URL 切替、段階リリース。大規模では IaC パラメータ管理（SSM/CloudFormation）と併用する。
  • よくある誤解: ステージ変数を秘密情報の置き場にすること。機密情報は Secrets Manager/SSM SecureString を使う。
  • 3分要点: ステージ変数は「環境差分の注入」に使う。機密管理とは分離する。

参考: Stage variables for REST APIs

S3 Event Notifications と重複イベント耐性
  • これは何か: S3 のオブジェクト作成/削除イベントを Lambda/SQS/SNS へ通知するイベント駆動機能。at-least-once 配信のため重複通知があり得る。
  • なぜ重要か: 非同期パイプライン構築の基本だが、重複や順不同を想定しないと本番で二重処理が起きる。
  • 使いどころ/使い分け: 画像変換、監査ログ転送、ETL起動。重複対策として DynamoDB に処理済みキー記録、またはオブジェクトメタデータで冪等制御する。
  • よくある誤解: 「S3通知は1回だけ届く」と考えること。試験でも実務でも冪等性は必須要件。
  • 3分要点: S3通知は便利だが重複前提。処理側を idempotent に作る。

参考: Amazon S3 Event Notifications

SNS フィルターポリシーで購読先を絞る設計
  • これは何か: SNS サブスクリプションごとに属性条件を定義し、必要なメッセージだけを配信するルーティング機能。
  • なぜ重要か: 発行側ロジックを複雑化せずに購読先ごとの分岐を実現できる。マイクロサービス連携の疎結合化に有効。
  • 使いどころ/使い分け: orderType や tenantId 単位で配信先を振り分ける。より厳密なイベントバス設計が必要なら EventBridge も候補。
  • よくある誤解: 受信側で全件受けてから捨てればよいという設計。不要トラフィックとコストを増やす。
  • 3分要点: フィルターポリシーは「発行1回・受信最小化」の要。属性設計を最初に決める。

参考: Amazon SNS message filtering

CodeBuild のキャッシュ戦略（S3/Local）
  • これは何か: 依存ライブラリやビルド成果物を再利用して、CodeBuild 実行時間を短縮する仕組み。S3 キャッシュと Local キャッシュがある。
  • なぜ重要か: CI コストと待ち時間を直接削減できる。試験では「最小の運用負荷でビルド高速化」選択肢として出やすい。
  • 使いどころ/使い分け: 安定的な共有には S3、同一ホスト再利用が効くケースは Local。再現性重視なら lockfile と併用してキャッシュ汚染を防ぐ。
  • よくある誤解: キャッシュを増やせば常に速くなると思うこと。キャッシュ復元時間が逆にボトルネックになる場合もある。
  • 3分要点: 速さだけでなく再現性と保守性でキャッシュ方式を選ぶ。

参考: CodeBuild build caching

KMS キーポリシーと IAM ポリシーの評価順
  • これは何か: KMS では IAM 許可だけでなくキーポリシーでもアクセス可否が決まる。両方の許可が揃って初めて利用可能になるケースが多い。
  • なぜ重要か: 「IAMで許可したのに暗号化できない」障害の主要原因。試験でも権限トラブルの原因特定問題でよく問われる。
  • 使いどころ/使い分け: 同一アカウント内はキーポリシーで IAM 利用を許可し、細粒度は IAM 側で制御。クロスアカウントは双方のポリシー調整が必要。
  • よくある誤解: KMS も他サービス同様に IAM だけで完結すると考えること。
  • 3分要点: KMS権限は「キーポリシー + IAM」の二段チェック。どちらが欠けても失敗する。

参考: AWS KMS key policies

CloudFront + OAC で S3 を非公開配信
  • これは何か: CloudFront Origin Access Control (OAC) を使い、S3 バケットをパブリック公開せずに CloudFront 経由のみで配信する構成。
  • なぜ重要か: セキュアな静的配信の現行ベストプラクティス。OAI からの移行文脈も含め、試験で狙われやすい。
  • 使いどころ/使い分け: SPA/画像配信/ダウンロード配布で、直接 S3 URL を無効化したいとき。署名付き URL/Cookie と組み合わせると会員限定配信にも対応。
  • よくある誤解: CloudFront を使えば S3 パブリック設定のままで良いという認識。実際はバケットポリシーを CloudFront のみに絞る必要がある。
  • 3分要点: OAC は「配信経路を CloudFront に固定して公開面を縮小する」設計。

参考: Restrict access to an Amazon S3 origin
