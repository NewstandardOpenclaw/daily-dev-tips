AWS DVA 対策（インプット特化）

2026-05-01 / 定義・重要性・使い分け・誤解・3分要点

Topic 1: DynamoDB パーティションキー設計とホットパーティション回避

定義

DynamoDB はパーティションキーの分散で性能が決まる。偏ったキーにアクセスが集中するとスロットリングが起きやすい。

重要性

  • DVA では「急なトラフィック増でレイテンシ悪化」の原因特定として頻出。
  • テーブル設定より先にアクセスパターン設計が問われる。

使い分け

  • 時系列ログ: ユーザーID#日付 などで分散。
  • ランキング: 書き込み経路を分け、集計を別テーブル化。
  • 単一キー集中が避けられない場合: DAX/キャッシュと書き込みシャーディング併用。

誤解

  • 誤: オンデマンドなら設計不要 → 正: 分散不良はオンデマンドでも詰まる。
  • 誤: GSIを増やせば解決 → 正: GSIも同じくキー偏りの影響を受ける。
実践課題: 「商品詳細APIで一部人気商品だけ秒間数千アクセス」のとき、キー設計・キャッシュ・再試行戦略を説明せよ。

3分要点

DynamoDB最適化の本丸はキー分散。容量モードより先にアクセス偏りを潰す。

Topic 2: Lambda 同時実行数（Reserved/Provisioned）とスロットリング対策

定義

Lambda の同時実行数はアカウント全体上限を共有。Reserved は関数への枠確保、Provisioned はコールドスタート抑制用の事前起動。

重要性

  • DVA の典型: 一部関数が全枠を使い切り他関数が失敗。
  • 性能改善と障害分離を同時に説明できるかが鍵。

使い分け

  • 重要API保護: Reserved concurrency を設定。
  • レイテンシ厳格: Provisioned concurrency + Auto Scaling。
  • 突発バースト: SQS/EventBridgeで平滑化。

誤解

  • 誤: Provisioned を上げればスロットリングも消える → 正: 上限管理は別問題。
  • 誤: 再試行だけで安定化できる → 正: バックプレッシャー設計が必要。
実践課題: 課金バッチが夜間に同時実行を食い尽くし、日中APIに影響。最小変更で守る手順を優先順位付きで示せ。

3分要点

Reserved=枠の隔離、Provisioned=起動遅延の削減。目的が違うので混同しない。

Topic 3: SQS 可視性タイムアウトと DLQ 設計

定義

可視性タイムアウト中は同一メッセージが他コンシューマーから見えない。処理失敗時は再出現し、規定回数超過で DLQ に移送できる。

重要性

  • 重複処理・取りこぼし・無限リトライを防ぐ中核設定。
  • DVA で「なぜ同じ処理が二重実行されたか」の説明点になる。

使い分け

  • 処理時間が可変: ChangeMessageVisibility で動的延長。
  • 恒久失敗が混在: maxReceiveCount を低めにしてDLQで切り分け。
  • 順序必須: FIFO + MessageGroupId（ただし並列性とのトレードオフ）。

誤解

  • 誤: 可視性タイムアウト=処理保証 → 正: 成功削除(DeleteMessage)まで保証されない。
  • 誤: DLQは最後の墓場 → 正: 再処理導線と監視まで設計して初めて価値が出る。
実践課題: 画像変換ジョブで一部だけ長時間処理になる。可視性タイムアウトとDLQをどう設計するか述べよ。

3分要点

SQSは「再試行前提」。可視性・削除・DLQの3点セットで安定運用を作る。
