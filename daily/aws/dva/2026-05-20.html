Topic 1: SQS Standard vs FIFO の使い分け

定義: SQS Standard は高スループット・少なくとも1回配信・順序保証なし。FIFO は厳密順序・重複排除（5分）・1回だけ処理に近づける設計。

重要性: DVAでは「順序必須か」「重複許容か」で即断できるかが頻出。設計の前提を間違えると後続実装が破綻する。

使い分け: 注文イベントの時系列処理は FIFO、ログ収集やバッチ投入は Standard。FIFO は MessageGroupId で並列度を調整する。

誤解: 「FIFO は常に遅い」は誤り。Group を分ければ十分なスループットを確保できるケースが多い。

3分要点:
1) 順序/重複が要件なら FIFO。
2) 大量処理優先なら Standard。
3) FIFO の性能鍵は MessageGroupId 設計。

Topic 2: Lambda の同時実行（Reserved vs Provisioned）

定義: Reserved Concurrency は関数ごとの上限/確保枠。Provisioned Concurrency は事前ウォームでコールドスタートを減らす仕組み。

重要性: DVAでは「スロットリング対策」か「レイテンシ安定化」かの意図で正解が分かれる。

使い分け: 他関数を守る隔離には Reserved。APIの初回遅延を減らすには Provisioned。両者併用も可能。

誤解: 「Provisioned を設定すれば無限に捌ける」は誤り。アカウント全体の同時実行上限は別管理。

3分要点:
1) Reserved=上限と保護。
2) Provisioned=低遅延。
3) 問題の軸（保護/速度）を先に特定。

Topic 3: DynamoDB の Conditional Write と楽観ロック

定義: Conditional Write は条件式が真のときだけ更新を許可。楽観ロックはバージョン属性で競合更新を検知する実装パターン。

重要性: 高並行環境でのデータ整合性はDVA頻出。単純上書きは競合バグを生みやすい。

使い分け: 在庫0未満防止には条件式、ユーザープロファイルの同時編集防止にはバージョン比較を使う。

誤解: 「DynamoDB はNoSQLだから整合性制御が弱い」は誤り。条件付き書き込みで強力に守れる。

3分要点:
1) 更新前提を条件式に明文化。
2) 競合はバージョンで検出。
3) 失敗時リトライ戦略までセットで設計。
