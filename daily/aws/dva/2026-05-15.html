AWS DVA 対策（インプット特化）- 2026-05-15

今日は「API 認可・キュー設計・Lambda 実行特性」をまとめて、選択肢のひっかけを見抜く練習に集中します。

Topic 1: API Gateway の IAM 認可 / Lambda オーソライザー / Cognito オーソライザー

定義: IAM認可はSigV4ベースのAWSプリンシパル向け。Lambdaオーソライザーは任意ロジックで認証・認可判定。CognitoオーソライザーはJWTトークン検証を標準化。

重要性: DVAでは「利用者の種類」と「トークン検証方法」に合う認可方式の選定問題が高頻度。

使い分け:
・社内ツールやAWS主体の呼び出し → IAM認可
・独自ヘッダー検証/外部認証連携 → Lambdaオーソライザー
・モバイル/SPAのユーザー認証基盤 → Cognitoオーソライザー

誤解: 「Lambdaオーソライザーが最強で常に正解」は誤り。運用負荷・レイテンシ・キャッシュ戦略を要比較。

3分要点: 呼び出し主体がAWSかエンドユーザーかを先に分ける。標準JWTならCognito、独自要件ならLambda、最短経路はIAM。

Topic 2: SQS Standard vs FIFO（重複・順序・スループット）

定義: Standardは高スループット優先で少なくとも1回配送。FIFOは順序保証と重複排除を提供。

重要性: 「順序必須か」「重複許容か」の2軸を誤ると、設計判断を外す典型論点。

使い分け:
・大量イベント処理で順序非依存 → Standard
・課金処理や在庫更新など順序/重複に厳密要件 → FIFO

誤解: 「FIFOなら重複が絶対ゼロ」は誤り。重複排除IDや処理側の冪等性設計は依然必要。

3分要点: 要件が“厳密順序”ならFIFO。そうでなければStandard＋コンシューマ冪等化が実務的。

Topic 3: Lambda 同時実行数（Reserved / Provisioned Concurrency）の実戦整理

定義: Reservedは関数ごとの同時実行枠の上限/確保。Provisionedは初期化済み実行環境を維持してコールドスタートを抑える。

重要性: DVAは性能問題で「レイテンシ要件」と「突発トラフィック耐性」の両立策を問う。

使い分け:
・他関数を守るためのリソース隔離 → Reserved
・常時低遅延API応答が必須 → Provisioned（必要ならAuto Scaling連携）

誤解: 「Provisionedを上げれば全コスト最適」は誤り。アクセス変動が大きいと過剰確保になりやすい。

3分要点: まずはReservedで暴走防止。厳しいレイテンシSLOがある部分だけProvisionedを局所適用。
