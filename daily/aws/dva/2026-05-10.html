Topic 1

Lambda Event Source Mapping のバッチ失敗制御（SQS/Kinesis/DynamoDB Streams）

定義

Event Source Mapping はストリーム/キューから Lambda へイベントを取り込む設定。Partial batch response を使うと、バッチ中の失敗レコードだけ再試行対象にできる。

重要性

DVA では「全部失敗扱いで再処理ループになる事故」をどう防ぐかが頻出。再試行粒度、DLQ/On-failure Destination、順序性の理解が点差になる。

使い分け

  • SQS: partial batch response で成功メッセージを消し、失敗分のみ再試行。
  • Kinesis/DynamoDB Streams: バッチ失敗時の再試行と shard 停滞リスクを考慮し、エラー隔離を設計。
  • BisectBatchOnFunctionError: 原因レコード特定を高速化したいとき（主に Kinesis/DDB Streams）。

よくある誤解

  • 誤解: Lambda 失敗時は常にバッチ全件再実行される → partial batch response で挙動を改善可能。
  • 誤解: DLQ を付ければ順序問題は解決する → FIFO や shard 順序は別設計が必要。

3分要点

  1. 失敗粒度を「全件」から「失敗レコードのみ」へ下げる設計が基本。
  2. 再試行回数と失敗退避先をセットで設計する。
  3. 順序性要件（FIFO/shard）とエラー隔離はトレードオフで判断する。
Topic 2

CodeDeploy Blue/Green（ECS/Lambda）のトラフィックシフト戦略

定義

Blue/Green は現行環境（Blue）と新環境（Green）を並行保持し、段階的にトラフィックを Green へ移すデプロイ方式。ECS/Lambda では CodeDeploy がシフト制御とロールバックを担う。

重要性

DVA では「無停止デプロイ」「自動ロールバック条件」「CloudWatch アラーム連携」の組み合わせ問題が高頻度。デプロイ設定名（Canary/Linear/AllAtOnce）も狙われる。

使い分け

  • Canary: 少量流して短時間で健全性確認し、問題なければ一気に切替。
  • Linear: 一定割合ずつ段階移行し、リスクを均す。
  • AllAtOnce: ダウンタイム許容または迅速切替優先時。

よくある誤解

  • 誤解: Blue/Green を使えば監視設定は不要 → アラーム未設定だと自動ロールバックが機能しない。
  • 誤解: Canary は必ず最も安全 → 低トラフィック環境では検知力不足で異常を見逃すことがある。

3分要点

  1. シフト方式は「検知速度」と「影響範囲」で選ぶ。
  2. CloudWatch アラーム連携がロールバック自動化の鍵。
  3. DVA では方式名と適用シナリオをセットで答える。
