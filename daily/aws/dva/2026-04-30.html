AWS DVA 対策（インプット特化）

2026-04-30 / 定義・重要性・使い分け・誤解・3分要点

Topic 1: API Gateway 認可方式（IAM / Cognito / Lambda Authorizer）

定義

  • IAM認可: SigV4 署名で AWS プリンシパルを検証。
  • Cognito Authorizer: JWT（主にユーザー）ベースで認可。
  • Lambda Authorizer: カスタムロジックでトークン検証・ポリシー返却。

重要性

DVA の頻出は「誰が呼ぶ API か」に応じた認可選定。誤選定すると運用負荷、レイテンシ、セキュリティ境界が崩れる。

使い分け

  • AWS内サービス・社内バッチ中心: IAM 認可。
  • モバイル/SPA の一般ユーザー: Cognito + JWT。
  • 独自ヘッダ検証、外部IdP統合、細粒度ABAC: Lambda Authorizer。

誤解

  • 誤: Lambda Authorizer は常に最強 → 正: 柔軟だが実行コストと遅延が増える。
  • 誤: Cognito を使えば API 権限設計不要 → 正: スコープ/クレーム設計は必須。
実践課題: 「社内ジョブ」と「一般ユーザーアプリ」が同一 API 群を利用。認可方式をエンドポイント単位で分ける方針を説明せよ。

3分要点

認可は“呼び出し主体”から逆算。IAM=AWS主体、Cognito=ユーザー主体、Lambda Authorizer=要件が標準外のとき。

Topic 2: ElastiCache（Redis）導入判断と TTL 設計

定義

ElastiCache はアプリ近傍に低レイテンシなインメモリ層を置き、読み取り頻度の高いデータやセッションを高速化する。

重要性

  • DVA では「DB負荷増」「レスポンス遅延」の改善策として頻出。
  • TTL の設計次第で整合性/鮮度/コストが変わる。

使い分け

  • 更新少・参照多: Cache-Aside（ミス時ロード）
  • 即時反映重視: Write-Through + 短TTL
  • 一時データ（認証コード等）: 厳格 TTL + 自動失効

誤解

  • 誤: キャッシュは常に正しい → 正: 失効戦略がないと古いデータ配信リスク。
  • 誤: TTLは長いほど得 → 正: ヒット率と鮮度のトレードオフ管理が必要。
実践課題: 商品価格APIで「1分以内の鮮度を保証しつつDB負荷を半減」するキャッシュ戦略を説明せよ。

3分要点

キャッシュは“速さ”だけでなく“失効設計”が本体。TTLは性能と正確性のバランスパラメータ。

Topic 3: S3 事前署名URL（Presigned URL）とセキュアアップロード

定義

Presigned URL は限定時間だけ有効な署名付きURL。クライアントがS3へ直接アップロード/ダウンロードでき、アプリサーバーの中継を減らせる。

重要性

  • 大容量ファイル処理の負荷分散に有効。
  • DVA で問われる「最小権限・短期資格情報」の具体例。

使い分け

  • 単発アップロード: PUT の Presigned URL。
  • ブラウザフォーム投稿: Presigned POST（条件制約を付与）。
  • 高機密: 有効期限短縮 + Content-Type 制約 + サーバー側検証。

誤解

  • 誤: URLを隠せば安全 → 正: 期限・権限・バケットポリシーで守る。
  • 誤: 長い有効期限でも問題ない → 正: 漏洩時の被害期間が伸びる。
実践課題: 画像アップロード機能で「不正ファイル抑止」と「モバイル低帯域対応」を両立する実装方針を述べよ。

3分要点

Presigned URL は“直接転送で性能向上”と“時間制限でリスク縮小”を両立。短命URL＋制約条件が基本。
