Lambda の同時実行制御（Reserved vs Provisioned Concurrency）
  • 定義: Reservedは関数ごとの上限・下限枠、Provisionedは事前ウォームした実行環境の確保。
  • 重要性: DVAでは「スロットリング回避」「コールドスタート最適化」の両面で頻出。
  • 使い分け: バースト抑制と隔離はReserved、低遅延APIはProvisioned。併用も可。
  • 誤解: Reservedを増やせば自動で低遅延になる、は誤り（低遅延はProvisioned側）。
  • 3分要点: 制限管理=Reserved、体感速度=Provisioned と覚える。

参考: AWS Lambda Concurrency

DynamoDB 読み込み整合性（Eventually vs Strongly Consistent）
  • 定義: Eventuallyは結果整合、Stronglyは直前書き込みを反映した読み込み。
  • 重要性: 正確性とコストのトレードオフ問題としてDVAで非常に出やすい。
  • 使い分け: 表示系はEventually、更新直後の検証や在庫確認はStronglyを検討。
  • 誤解: GSIでもStrongly Consistent Readできる、は誤り（GSIはEventuallyのみ）。
  • 3分要点: 整合性を上げるとコストとレイテンシも上がる を前提に設計する。

参考: DynamoDB Read Consistency

質問テンプレ: 「DynamoDB整合性の使い分けを、業務シナリオ付きで3例」
API Gateway のキャッシュとスロットリング
  • 定義: キャッシュはバックエンド負荷軽減、スロットリングは過負荷防止のレート制御。
  • 重要性: コスト最適化と可用性維持を同時に問う設問で使われる。
  • 使い分け: 読み取り中心APIはキャッシュ、悪意/突発アクセス対策はUsage Plan + Throttle。
  • 誤解: キャッシュ有効化だけで常に高速化、は誤り（TTL設計とヒット率次第）。
  • 3分要点: 速くする機能と守る機能は別。両輪で設計する。

参考: API Gateway Caching

質問テンプレ: 「API Gatewayで性能と保護を両立する設計案を出して」
SQS 可視性タイムアウトとDLQの設計
  • 定義: 可視性タイムアウトは再処理までの待機時間、DLQは失敗メッセージ退避先。
  • 重要性: 重複処理や取りこぼしを防ぐ中核設定で、運用トラブル系の問題で頻出。
  • 使い分け: 処理時間より少し長めの可視性、maxReceiveCountは暫定障害回復回数で決める。
  • 誤解: 可視性を極端に長くすれば安全、は誤り（障害時の復旧が遅れる）。
  • 3分要点: 処理時間分布に合わせて可視性を調整し、DLQで観測可能にする。

参考: SQS DLQ

質問テンプレ: 「SQSの可視性タイムアウト設計を、実運用目線でレビューして」
CodeDeploy のデプロイ方式（In-Place vs Blue/Green）
  • 定義: In-Placeは既存環境へ順次更新、Blue/Greenは新旧環境を並行して切替。
  • 重要性: 可用性要件・ロールバック戦略の判断問題としてDVAで定番。
  • 使い分け: コスト重視はIn-Place、停止最小化と安全切替はBlue/Green。
  • 誤解: Blue/Greenは常に高コストで無意味、は誤り（障害時損失低減で逆転する）。
  • 3分要点: 失敗時の戻しやすさ を評価軸に選択する。

参考: CodeDeploy Deployment Types

質問テンプレ: 「CodeDeploy方式選定を、試験問題風に比較して」
