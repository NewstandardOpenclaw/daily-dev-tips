Topic 1

API Gateway + Lambda のエラーハンドリング設計

定義

クライアント向けHTTPレスポンスと、Lambda内部の例外を分離して設計すること。API Gateway 側で statusCode とボディ整形を安定化し、Lambda 側は業務エラー（4xx）とシステムエラー（5xx）を明示的に分類する。

重要性

  • DVAで頻出: 「正しいHTTPコード」「再試行可否」「監視しやすさ」の同時達成。
  • 運用で必須: 失敗原因を CloudWatch Logs / X-Ray で追跡しやすくなる。

使い分け

  • 4xx: バリデーション失敗、認可失敗、リソース不在（クライアント修正が必要）。
  • 5xx: タイムアウト、依存サービス障害、一時的失敗（リトライ設計対象）。
  • Lambda proxy統合: 実装自由度高。非proxy: マッピングテンプレートで統制しやすい。

誤解しがち

  • 「例外なら全部500」→ 試験ではNG。業務エラーは4xxに寄せる。
  • 「エラー文を詳細表示ほど親切」→ セキュリティ上は内部情報の露出に注意。

3分要点

  • 業務エラー4xx / システムエラー5xxを明確に分離。
  • 再試行可否をHTTPコードで示すと、クライアント実装が安定。
  • CloudWatchメトリクス（4XXError, 5XXError）とログ設計をセットで覚える。

Topic 2

DynamoDB: 強い整合性読み取り vs 結果整合性

定義

DynamoDBの読み取り整合性モード。強い整合性は直前書き込みを必ず反映、結果整合性は低レイテンシ/低コストだが最新反映に短い遅延があり得る。

重要性

  • 試験で定番: 「正しさ優先」か「性能・コスト優先」かの選択問題。
  • 実務で重要: 在庫/残高/重複防止など、誤読が許されない要件で差が出る。

使い分け

  • 強い整合性: ユーザー直後確認、排他制御前の再読、厳密表示。
  • 結果整合性: タイムライン、ランキング、分析系ダッシュボード。
  • 注意: GSIは結果整合性のみ。強い整合性はテーブル/LSI読み取りで検討。

誤解しがち

  • 「常に強い整合性が正解」→ コスト・スループットに不利な場合がある。
  • 「結果整合性は信用できない」→ 多くの参照系で十分実用。

3分要点

  • 厳密性が必要なら強い整合性、通常は結果整合性を基本にする。
  • GSIでは強い整合性を選べない点を必ず暗記。
  • ユースケースで説明できるとDVAの消去法が強くなる。

Topic 3

SQS 可視性タイムアウトとDLQの設計

定義

SQSメッセージ受信後、処理中は他コンシューマーから不可視にする時間が可視性タイムアウト。失敗を繰り返すメッセージを隔離する仕組みがDLQ（Dead-Letter Queue）。

重要性

  • DVAで頻出: 重複処理回避、再処理戦略、障害切り分け。
  • 運用で重要: 「詰まり続ける毒メッセージ」を本流から隔離できる。

使い分け

  • 処理が長いなら可視性タイムアウトを延長（必要なら動的変更）。
  • 一時障害は再試行、本質的に壊れたデータはDLQ隔離。
  • Lambdaトリガー時はバッチサイズ・再試行回数・最大受信回数をセットで設計。

誤解しがち

  • 「DLQに行けば解決」→ 解析・再投入フローがないと負債化する。
  • 「可視性タイムアウトは長いほど安全」→ 障害時の復旧遅延を招く。

3分要点

  • 可視性タイムアウトは処理時間に合わせる（短すぎ/長すぎ両方NG）。
  • DLQは隔離箱。運用Runbook（原因分析→修正→再投入）までが設計。
  • DVAでは「重複回避」「再試行」「毒メッセージ」を同時に見る。
