Topic 1: DynamoDB のキー設計（PK/SK）と Query 前提思考

定義

PK（パーティションキー）はデータ分散、SK（ソートキー）は同一PK内の並びと範囲検索を担う。DynamoDBは「あとから自由検索」ではなく、先にアクセスパターンを定義してテーブル設計するDB。

重要性

  • DVAでは「Scan多用」より「Query中心設計」が高頻度出題。
  • RCU/WCU最適化、レイテンシ最小化、ホットパーティション回避に直結。

使い分け

  • 主導線: Query（PK必須、SK条件で絞る）
  • 補助導線: GSI（別キーで検索導線を追加）
  • 緊急/一時: Scan（コスト高・本番常用は避ける）

誤解

  • 誤: FilterExpressionで安くなる → 正: 読み取り後に除外なのでRCU節約になりにくい。
  • 誤: GSIは無料で柔軟性だけ増える → 正: 追加の書き込み/ストレージコストがある。
実践課題: 「注文テーブル」で「ユーザー別の最新20件」と「商品ID別の直近注文」を同時に満たすPK/SK+GSI設計を説明せよ。

3分要点

DynamoDBはクエリ先行設計。PK/SKで主経路、GSIで別経路、Scanは最後の手段。FilterExpressionは読み取りコストを魔法のようには下げない。

Topic 2: SQS vs SNS vs EventBridge のイベント設計

定義

  • SQS: メッセージキュー（pull、耐障害、バックプレッシャー吸収）
  • SNS: Pub/Sub（push、複数購読者への同報）
  • EventBridge: ルールベースイベントバス（フィルタ/ルーティング、SaaS連携）

重要性

DVAでは「要件から最適サービスを選ぶ」問題が中心。順序保証、再試行、疎結合の設計意図を説明できるかが得点差になる。

使い分け

  • ワーカー処理の平準化・再処理: SQS（必要ならDLQ）
  • 同時通知（メール/HTTP/Lambda）: SNS
  • イベント属性で動的振り分け: EventBridge

誤解

  • 誤: SNSがあればキュー不要 → 正: 消費者障害時のバッファはSQSが強い。
  • 誤: EventBridgeは単なるSNS上位互換 → 正: 目的が違う（ルールベース統合/バス設計）。
実践課題: EC注文イベントで「在庫更新」「請求」「分析基盤転送」を疎結合に実装。どのサービスをどこで使うか図なしで説明せよ。

3分要点

SQS=ためる、SNS=配る、EventBridge=振り分ける。要件（再試行・同報・ルール）から逆算して選ぶ。

Topic 3: Lambda の同時実行と失敗ハンドリング（再試行/DLQ）

定義

Lambdaはイベントソースに応じて同期/非同期で実行され、同時実行（Concurrency）制御とエラー処理（再試行、DLQ、on-failure destination）が可用性とコストを左右する。

重要性

  • スパイク時のダウンストリーム保護（DB枯渇防止）
  • 失敗メッセージの追跡性（データロス防止）

使い分け

  • Reserved Concurrency: 関数ごと上限/下限を確保し暴走抑制
  • SQSトリガー: バッチサイズ・可視性タイムアウト調整
  • 非同期呼び出し: 再試行設定 + DLQ/Destinationで失敗回収

誤解

  • 誤: タイムアウトだけ伸ばせば解決 → 正: 根本は並列度/下流容量/リトライ設計。
  • 誤: DLQがあれば可観測性は十分 → 正: CloudWatch Logs/Metrics/Alarmsとセット運用が必要。
実践課題: 外部API呼び出しLambdaでレート制限超過が発生。可用性を落とさず失敗を回収する設定変更案を3つ提示せよ。

3分要点

Lambda運用は「並列度の制御」と「失敗の行き先設計」が核心。成功率だけでなく、失敗時の回収経路を必ず設計する。
