Topic 1

API Gateway Lambda オーソライザー（JWT/Cognito）

定義

API Gateway で受けたトークンを検証し、リクエストの実行可否を判定する仕組み。HTTP API では JWT オーソライザー、REST API では Lambda オーソライザー（TOKEN/REQUEST）がよく問われる。

重要性

DVA 試験では「認証は通ったが認可が不十分」「キャッシュ設定ミスで意図しない許可」が頻出。とくに authorizer result cache とトークン失効の関係が狙われやすい。

使い分け

  • JWT オーソライザー: OIDC/JWT をそのまま検証。高速・構成が簡単。
  • Lambda オーソライザー: 柔軟な判定ロジック（DB参照、複数ヘッダ条件）。複雑要件向け。
  • Cognito User Pool オーソライザー: モバイル/SPA の標準実装で採用しやすい。

よくある誤解

  • 誤解: 認証できれば最小権限は自動で守られる → 実際は IAM/ポリシー設計が別途必要。
  • 誤解: キャッシュは常に有効化すべき → トークン失効即時反映が必要なら TTL 短縮/無効化を検討。

3分要点

  1. 「高速・標準」なら JWT、「柔軟判定」なら Lambda。
  2. キャッシュTTLはセキュリティ要件とトレードオフ。
  3. 認可失敗時の HTTP ステータス（401/403）を設計で明確化。
Topic 2

DynamoDB 条件付き書き込み（ConditionExpression）と楽観ロック

定義

ConditionExpression により「条件を満たす場合だけ書き込む」を実現。競合更新を防ぐにはバージョン属性を使う楽観ロックが定番。

重要性

DVAでは「上書き事故をどう防ぐか」「同時更新時にどの例外が返るか（ConditionalCheckFailedException）」が典型問題。トランザクション不要なケースの判断が鍵。

使い分け

  • ConditionExpression: 単一アイテム更新の整合性担保。
  • TransactWriteItems: 複数アイテムの原子性が必須な場合。
  • Optimistic Locking: 更新衝突を検出して再試行戦略に接続。

よくある誤解

  • 誤解: Condition を付ければ自動で再試行される → SDK のリトライは失敗理由次第、業務再試行は実装が必要。
  • 誤解: トランザクションは常に最善 → レイテンシ/コスト増、要件に応じて使い分ける。

3分要点

  1. まず単一アイテムなら ConditionExpression を優先。
  2. 衝突検出時は ConditionalCheckFailedException を期待動作として扱う。
  3. 複数アイテム原子性が必要な時だけ TransactWriteItems。
