Topic 1: API Gateway の認可方式を定義で整理

定義: API Gateway の主要認可は AWS_IAM、Lambda Authorizer（TOKEN/REQUEST）、Cognito User Pools。

重要性: DVAでは「誰が呼ぶAPIか」で最適解が変わる。認可方式の誤選択は実装コストと運用負荷を増やす。

使い分け: AWS内サービス主体→IAM。独自トークン検証→Lambda Authorizer。モバイル/WEBログイン基盤→Cognito。

誤解: 「Cognitoを使えば全API要件を自動で満たす」は誤り。細粒度権限制御は追加設計が必要。

3分要点: 呼び出し主体（人/サービス）とトークン形態（SigV4/JWT独自）を先に確定する。

Topic 2: Lambda Authorizer のキャッシュと落とし穴

定義: Lambda Authorizer は認可結果をTTL付きでキャッシュ可能。毎回Lambda実行を避けてレイテンシとコストを下げる。

重要性: 試験は「性能最適化」と「即時失効」のトレードオフを問う。TTL設定の意味理解が得点源。

使い分け: 高頻度APIかつ権限変化が少ない→TTLを長め。権限剥奪を即時反映したい→TTL短め/無効化。

誤解: 「キャッシュは常に正義」ではない。退職者アカウント無効化など即時性要件と衝突する。

3分要点: 認可の鮮度要件（何秒で反映必須か）を先に決めてTTLを置く。

Topic 3: 試験で迷う「最小運用で安全」な選び方

定義: DVAの選択肢は「マネージド優先・カスタム最小」の原則で解くと正答率が上がる。

重要性: 同じ要件でも実装自由度が高い選択肢は不正解になりやすい。運用負荷が低い構成が正解候補。

使い分け: 既存IdP連携が不要ならCognito優先。独自ルール必須ならAuthorizer。サービス間はIAM第一。

誤解: 「柔軟性が高いほどベスト」は誤り。試験は通常、要件を満たす最小構成を評価する。

3分要点: “要件を満たす中で最もシンプル” を選ぶ。追加実装が多い選択肢は一歩引いて再評価。
