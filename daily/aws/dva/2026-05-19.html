Topic 1: Lambda 再試行・DLQ・On-failure Destination の使い分け

定義: Lambdaの非同期呼び出しは自動再試行があり、最終失敗時にDLQ（SQS/SNS）またはDestinationへ結果送信できる。DLQは失敗イベント退避、Destinationは成功/失敗のルーティングに強い。

重要性: DVA頻出の「失敗したイベントをどう回収し、どこで再処理するか」の判断軸になる。

使い分け:
・失敗イベントを単純に溜めて後で確認 → DLQ
・失敗時にStep Functionsや別Lambdaへ自動連携 → On-failure Destination
・同期呼び出し(API経由)での失敗はクライアント応答設計が中心（DLQ前提ではない）

誤解: 「LambdaにDLQを設定すれば全部の失敗を捕まえられる」は誤り。同期実行失敗やサービス前段での拒否は別経路で観測が必要。

3分要点: 非同期失敗回収は DLQ=保管、Destination=次アクション連携。問題文で“何をしたいか”を先に読む。

Topic 2: DynamoDB の Eventually Consistent Read vs Strongly Consistent Read

定義: Eventually Consistent Readは低コストで高スループットだが直近更新が見えない可能性がある。Strongly Consistent Readは最新反映を保証するがコスト/性能面で制約が増える。

重要性: DVAでは「正確性優先か、スループット・コスト優先か」の典型的トレードオフとして頻出。

使い分け:
・画面表示や分析系で若干の遅延許容 → Eventually
・更新直後の在庫確認や二重処理防止判定 → Strongly
・GSIは強整合読み取り不可（ここを問うひっかけあり）

誤解: 「Stronglyを常に使えば安全で正解」は誤り。不要に使うとコスト増・スケール低下を招く。

3分要点: 要件文の“直後に必ず最新必要か”で分岐。必要な箇所だけStronglyに限定する。

Topic 3: API Gateway 認証方式（IAM / Cognito User Pools / Lambda Authorizer）

定義: IAM認証はAWS署名ベース、Cognito User Poolsはユーザー認証基盤連携、Lambda Authorizerは独自ロジックでトークン検証する方式。

重要性: DVA問題で「どのクライアントがAPIを叩くか」によって最適解が変わる代表例。

使い分け:
・AWS内サービスやCLI主体でSigV4利用可能 → IAM
・モバイル/Webユーザーのサインイン連携 → Cognito User Pools
・外部IdPや独自クレーム評価が必要 → Lambda Authorizer

誤解: 「Lambda Authorizerが最も柔軟だから常に最適」は誤り。運用負荷・レイテンシ増を伴うため必要時のみ採用。

3分要点: 認証方式は“クライアント種別と運用負荷”で決める。柔軟性とシンプルさのバランスが得点ポイント。
