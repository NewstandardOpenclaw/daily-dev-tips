AWS DVA 対策（インプット特化）

Topic 1: API Gateway のスロットリングと Usage Plan の役割分離

定義

API Gateway にはアカウント/ステージ/メソッド単位のスロットリングがあり、Usage Plan は API キーごとのレート・バースト・クォータを制御する仕組み。

重要性

  • DVA で「特定顧客だけ過剰アクセス」の制御策を聞かれる定番テーマ。
  • 全体保護（ステージ）と契約別制御（Usage Plan）を分けて説明できると強い。

使い分け

  • 全体保護: ステージ/メソッド側で上限を設定。
  • 顧客別制御: Usage Plan + API Key で Tier ごとの制限。
  • 認可要件が強い場合: Cognito/JWT 認証を併用し、API Key を認証用途に流用しない。

誤解

  • 誤: API Key は認証そのもの → 正: 主用途は利用量制御・識別。
  • 誤: Usage Plan だけで API 全体を守れる → 正: 基盤側のスロットリング設定も必要。
実践課題: 無料プラン利用者の急増で 429 が頻発。全体の可用性を守りつつ有料ユーザー体験を維持する設定順序を説明せよ。

3分要点

API Gateway は「全体防御」と「顧客別制御」の二段構え。API Key は認証ではなく利用管理寄り。

Topic 2: CloudFront キャッシュキー設計（Headers/Cookies/Query Strings）

定義

CloudFront はキャッシュキーに含める要素（ヘッダー、Cookie、クエリ）でヒット率と正確性が決まる。不要な要素を含めるとキャッシュが分断される。

重要性

  • DVA の性能問題シナリオで「ヒット率低下→オリジン過負荷」は高頻度。
  • 正しいキャッシュキー設計はコストとレイテンシの両方に効く。

使い分け

  • 静的配信: クエリ/ヘッダー/Cookie を最小化。
  • 言語別表示: 必要な Accept-Language だけをキー化。
  • 署名付きURL配信: 認可情報はオリジン検証に寄せ、不要なキー肥大を避ける。

誤解

  • 誤: 動的要素は全部キーに入れるべき → 正: 必要最小限だけ含める。
  • 誤: TTL を伸ばせばヒット率は自動改善 → 正: キー分断が原因ならTTLだけでは解決しない。
実践課題: ECサイトで ?utm_* 付きURL流入が増え、キャッシュミスが急増。どの設定をどう直すか述べよ。

3分要点

CloudFront 最適化は TTL より先にキャッシュキー。変化に関係ない属性はキーに入れない。

Topic 3: Step Functions の再試行（Retry）と補償（Catch）設計

定義

Step Functions では Retry で一時的失敗に自動再試行し、Catch で失敗時の分岐（通知・ロールバック・代替処理）を定義できる。

重要性

  • DVA で「ワークフローの堅牢化」を問う設問に直結。
  • Lambda 側に再試行を埋め込むより、オーケストレーション層で統制すると可観測性が高い。

使い分け

  • 一時障害: Exponential Backoff の Retry。
  • 業務的失敗: Catch で補償トランザクションへ遷移。
  • 外部API呼び出し: タイムアウト短縮 + 冪等設計をセットで実施。

誤解

  • 誤: Retry 回数を増やせば信頼性が上がる → 正: 障害種別ごとに上限と待機時間を調整すべき。
  • 誤: Catch は最終ログ用だけ → 正: 失敗後の業務整合性を保つ本体ロジック。
実践課題: 注文処理フローで「決済成功後に在庫引当失敗」が発生。Retry/Catch/補償アクションをどう設計するか説明せよ。

3分要点

Retry は一時障害対策、Catch は業務整合性対策。両方を分けて設計するのがDVA解法。
