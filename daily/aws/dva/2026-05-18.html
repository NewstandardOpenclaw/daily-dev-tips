Topic 1: IAM ロール vs Secrets Manager vs SSM Parameter Store（SecureString）

定義: IAMロールは一時的な認証情報を安全に付与する仕組み。Secrets Managerは機密情報（DBパスワード等）を保存・ローテーション管理するサービス。Parameter Storeは設定値管理が主用途で、SecureStringで暗号化保存も可能。

重要性: DVAでは「コード内に秘密情報を埋め込まない設計」が繰り返し問われる。

使い分け:
・AWS API 呼び出し権限をアプリに与える → IAMロール
・定期ローテーション付きの機密情報管理 → Secrets Manager
・低コストで設定値中心の集中管理 → Parameter Store

誤解: 「IAMロールがあればDBパスワード保管も不要」は誤り。ロールは“権限”であり、外部DB等の“秘密値”そのものは別管理が必要。

3分要点: 権限はロール、秘密値はSecrets/Parameter。役割を混同しないだけで選択肢の切り分けが速くなる。

Topic 2: CloudFront キャッシュ戦略（TTL・Invalidation・バージョニング）

定義: CloudFrontはエッジでコンテンツをキャッシュ配信するCDN。TTLはキャッシュ保持時間、Invalidationは手動削除、バージョニングは新しいファイル名で更新を反映する手法。

重要性: DVAでは「更新反映速度とコストのバランス」を問うケースが多い。

使い分け:
・頻繁更新しない静的アセット → 長めTTL + ファイル名バージョニング
・緊急で古い配信を止めたい → Invalidation
・動的に鮮度を制御したい → Cache-Control ヘッダ調整

誤解: 「更新のたびに毎回Invalidationが最適」は誤り。高頻度更新はバージョニングの方がスケールしやすい。

3分要点: 通常運用はバージョニング中心、緊急時のみInvalidation。TTLは要件に合わせて設計。

Topic 3: SQS 標準キュー vs FIFO（順序保証・重複処理）

定義: SQS標準キューは高スループットで少なくとも1回配送。FIFOキューは順序保証と重複排除を提供する。

重要性: DVAでは「順序保証が本当に必要か」を見極める問題が定番。

使い分け:
・最大スループット重視、多少の重複をアプリで吸収可能 → 標準キュー
・厳密な順序処理や重複回避が必須 → FIFOキュー（MessageGroupId/重複排除IDを活用）

誤解: 「FIFOなら設計不要で完全無欠」は誤り。グループ設計を誤ると並列性が落ちる。

3分要点: 要件が“順序必須”か“高スループット優先”かを先に決める。FIFO採用時はMessageGroup設計までセットで考える。
