Topic 1

API Gateway の Lambda オーソライザー（REQUEST vs TOKEN）

定義

Lambda オーソライザーは API Gateway で実行されるカスタム認可。TOKEN は単一トークンを検証、REQUEST はヘッダー・クエリ・パス・ステージ変数など複数入力を使って認可判定する。

重要性

DVA では「どの情報を認可判定に使うべきか」「キャッシュキー設計」「Cognito との使い分け」が定番。認可失敗時のレスポンス制御も頻出。

使い分け

  • TOKEN: Bearer トークン1本で単純・高速に判定したい時。
  • REQUEST: テナントIDやHTTPメソッド、リソースパスを含めて柔軟に判定したい時。
  • Cognito User Pool Authorizer: JWT検証をマネージドで簡素化したい時。

よくある誤解

  • 誤解: REQUEST の方が常に優れている → 判定軸が増える分、キャッシュ設計を誤るとレイテンシ悪化。
  • 誤解: オーソライザーがあれば IAM 認可は不要 → API 種別によっては IAM 連携が最適なケースもある。

3分要点

  1. 単純検証は TOKEN、複合判定は REQUEST。
  2. 認可キャッシュのキー設計が性能と正確性を左右。
  3. 「Lambda Authorizer / Cognito / IAM」の三択を要件で説明できるようにする。
Topic 2

DynamoDB 条件付き書き込み（ConditionExpression）で競合を防ぐ

定義

ConditionExpression は「条件が真のときだけ書き込み」を保証する仕組み。楽観ロック（version属性）や重複登録防止（attribute_not_exists）に使う。

重要性

DVA では「同時更新でデータ破壊を避けるには？」という実務問題が多い。トランザクションを使わずとも、条件付き書き込みで整合性を確保できる場面を問われる。

使い分け

  • attribute_not_exists(PK): 新規作成の重複防止。
  • version = :v: 楽観ロックで更新競合検出。
  • TransactWriteItems: 複数アイテムの原子的整合が必要な場合。

よくある誤解

  • 誤解: 条件失敗はシステム障害 → 多くは期待通りの競合検知で、再取得して再試行する設計が正解。
  • 誤解: 競合対策は常にトランザクション必須 → 単一アイテムなら ConditionExpression で十分なことが多い。

3分要点

  1. 単一アイテム競合は ConditionExpression が第一候補。
  2. ConditionCheckFailedException は業務フローで吸収する。
  3. 複数アイテム整合だけ TransactWriteItems を検討。
