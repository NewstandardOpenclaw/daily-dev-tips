eBPFで観測を拡張する基礎
  • 定義: カーネル内部イベントを安全にフックし、低オーバーヘッドで計測する技術。
  • 重要性: アプリ改修なしでネットワーク遅延やシステム挙動を可視化しやすい。
  • 使い分け: まず観測用途で導入し、制御用途は権限設計と検証を厚くして段階導入する。
  • よくある誤解: eBPFを入れるだけで自動的に性能問題が解決するという誤解。
  • 3分要点: 「何を測るか」を先に固定し、1ユースケースから小さく検証する。

参考: eBPF.io / Brendan Gregg

質問テンプレ: 「eBPFを、定義→重要性→使い分け→誤解→3分要点の順で、観測用途中心に解説してください。」
Event Sourcingの導入境界
  • 定義: 現在状態ではなくイベント履歴を正とし、再生して状態を復元する設計。
  • 重要性: 監査性や変更履歴の追跡に強く、業務の時系列理解を深められる。
  • 使い分け: 監査要件が高いドメインに限定導入し、全サービス一律適用は避ける。
  • よくある誤解: Event Sourcingを入れればDB設計が単純になるという誤解。
  • 3分要点: リプレイ時間・スナップショット戦略・イベント進化方針を最初に決める。

参考: Martin Fowler / Azure Pattern

質問テンプレ: 「Event Sourcingを、定義→重要性→使い分け→誤解→3分要点の順で、導入判断の観点付きで説明してください。」
RAGにおける再ランキング設計
  • 定義: 初期検索で得た候補文書を、関連度モデルで再評価して並び替える工程。
  • 重要性: 回答品質のばらつきを減らし、誤引用や文脈外回答を抑えられる。
  • 使い分け: 低遅延優先なら上位数件のみ再ランク、高精度優先なら段階的再ランクを採用。
  • よくある誤解: ベクトル検索の次元数を増やせば再ランキングは不要という誤解。
  • 3分要点: 検索精度は「リコール確保→再ランクで精度向上」の2段で考える。

参考: Rerankers Guide / LangChain RAG

質問テンプレ: 「RAG再ランキングを、定義→重要性→使い分け→誤解→3分要点の順で、実装選択肢込みで解説してください。」
Chaos Engineeringの最小実践
  • 定義: 障害を意図的に注入し、システムの回復力を検証・改善する手法。
  • 重要性: 想定外障害への対応力を平時に鍛え、実障害時の混乱を減らせる。
  • 使い分け: まず非本番で小規模に実施し、ガードレール整備後に本番限定実験へ広げる。
  • よくある誤解: 派手な障害注入をしないと効果がないという誤解。
  • 3分要点: 仮説・停止条件・ロールバック手順を1ページで明文化してから実行する。

参考: Principles of Chaos / Chaos Monkey

質問テンプレ: 「Chaos Engineeringを、定義→重要性→使い分け→誤解→3分要点の順で、最小実践プラン付きで教えてください。」
Token Bucketによるレート制御
  • 定義: トークン蓄積量で許可数を調整し、短時間バーストと平均流量を両立する制御法。
  • 重要性: 突発アクセス時の過負荷を抑えつつ、通常時の応答性を維持できる。
  • 使い分け: API入口はToken Bucket、下流保護には同時実行制限を併用する。
  • よくある誤解: レート制御は不正アクセス対策だけが目的という誤解。
  • 3分要点: バースト許容量と補充速度を業務トラフィックに合わせて分離設計する。

参考: Token Bucket / Rate Limiting Design

質問テンプレ: 「Token Bucketを、定義→重要性→使い分け→誤解→3分要点の順で、設定値の決め方付きで解説してください。」
